# Проверка CutCraft перед PR

Работай из корня репозитория. Прочитай AGENTS.md, README.md и docs/CONTRACTS.md именно в проверяемой ветке: main и незамерженные ветки могут иметь разные возможности.

## Определить изменения

Уточни целевую ветку по задаче или настройкам репозитория. Проверь текущую ветку, состояние файлов и diff от merge-base с целевой веткой; отдельно просмотри staged и unstaged изменения. Если remote не удалось обновить, укажи, на каком локальном снимке выполнена проверка. Не переключай ветку с чужими изменениями и не включай их в коммит.

Проверь только относящиеся к задаче файлы. Не выводи содержимое .env, приватных ключей и токенов. Убедись по именам отслеживаемых и подготовленных файлов и доступному diff, что секреты, пользовательские видео, output, кэш и настройки IDE не попадают в изменение. Не заявляй полный аудит истории на основании проверки одного diff. Обнаруженный секрет не цитируй; останови публикацию и сообщи, что требуется удалить его и заменить скомпрометированный ключ.

## Проверить результат

- Выполни `git diff --check` для изменения относительно целевой ветки и для локальных правок.
- По правилам проекта запусти `python3 -m unittest discover -s tests -v` и `python3 main.py --demo`. Сбой окружения отделяй от дефекта реализации; не выдавай непройденную проверку за успешную.
- Проверь созданную раскадровку и JSON-результаты на соответствие сценарию изменения. Артефакты оставь в игнорируемом output. Для чисто документационной правки достаточно проверить успешное создание демо и актуальность ссылок/команд; глубокую проверку неизменённого рендера повторять не требуется.
- При изменении форматов сопоставь docs/CONTRACTS.md, существующие schemas, contracts.py, примеры, prompts и потребителей. Проверяй границы фрагментов, цитаты, полноту review, сохранение принятых сцен и остановку на needs_human_review там, где это затронуто изменением. Не требуй файлов, которых ещё нет в проверяемой ветке.
- Различай фиксированное демо, реальные API-вызовы и проверку на настоящих кадрах. Успех демо не доказывает работу LLM или мультимодального критика. README и описание PR должны отражать фактическую реализацию.

Реальные API-вызовы не являются обязательной проверкой перед каждым PR: они расходуют квоту и передают данные провайдеру. Запускай их только в авторизованном объёме; не меняй модель на платную ради прохождения проверки. Используй существующие результаты, явно указав их давность и область применимости.

## Отчёт

Кратко укажи: что проверено и относительно какой ветки; результаты команд; подтверждённые проблемы с файлами/строками; что не проверено и почему. Отдельно отметь, мешают ли найденные проблемы публикации. Не создавай формальные тесты, которые лишь повторяют текст skill или реализацию.

Этот skill проверяет готовность. Коммит, push, создание PR и merge выполняй только в рамках явного запроса пользователя; успешная проверка сама по себе такого разрешения не даёт. Не сливай другие открытые PR вместе с проверяемым изменением.
