# Контракты CutCraft

Работай от корня репозитория. Прочитай `AGENTS.md`, `docs/CONTRACTS.md`, `docs/adr/0002-json-contracts.md`, относящиеся `schemas/*.schema.json`, `contracts.py` и `examples/`. Не определяй формат по случайному ответу модели.

## Три границы

- `catalog`: данные Артёма → монтажёр, проверяющий и оркестратор. Сегменты, таймкоды, транскрипт, относительные пути кадров.
- `plan`: монтажёр Марины → проверяющий Галима и оркестратор Кирилла. Сцены с выбранными сегментами, подписями и цитатами.
- `review`: проверяющий → монтажёр и оркестратор. Одно решение по каждой сцене, свидетельство и конкретная правка.

Текущие ограничения 1.0: ровно три сцены на 20–30 секунд, уникальные ID, известные поля, существующие сегменты, цитата как точная подстрока transcript. Это текущий договор проекта; не превращать его в универсальный стандарт и не менять без задачи.

## Как менять контракт

1. Установить производителя, потребителей и конкретное несовпадение. Проверить публичные сигнатуры `build_plan`, `revise_plan`, `review_plan`, а также вызовы в CLI/оркестраторе.
2. Разделить форму данных и смысловые/межфайловые условия. JSON Schema Draft 2020-12 задаёт типы, required, enum и форму; Python проверяет связи, длительность, цитаты и правила доработки.
3. При несовместимом изменении описать версию и переход потребителей. В 1.0 неизвестные поля запрещены: добавление поля затронет строгих потребителей, даже если оно кажется необязательным.
4. Согласованно обновить схемы, runtime-валидаторы, потребителей, документацию и эталонные примеры. Не ослаблять проверки только потому, что модель вернула неверный ответ.
5. Добавить содержательные позитивные и негативные проверки, связанные с изменением. Охватить затронутые границы, а не проверять только одинаковые строки в схеме и документации.

## Инварианты доработки

`validate_revision` сохраняет scene_id и значения принятых сцен. Если все решения accept, новый запрос не нужен; needs_human_review останавливает автоматическое исправление. Проверить существование ID и тип до set/dict lookup; bool не считать числовым таймкодом, NaN/Infinity недопустимы.

Точная цитата и валидный JSON не доказывают верность подписи или соответствие картинки. Не выдавать техническую проверку за фактчекинг/визуальный анализ.

## Примеры и проверка

`examples/` — общие контрольные примеры. Реальные материалы лежат в `data/`; не подменять эталонный пример персональным видео. После осознанного изменения формата обновлять примеры вместе с проверками.

Из корня:

```bash
python3 -m unittest discover -s tests -v
python3 main.py --demo
```

Если нужна внешняя проверка JSON Schema, использовать совместимый Draft 2020-12 валидатор при его наличии; не утверждать, что такой прогон выполнен, если проверен только runtime-код. Новый API-запрос не нужен для обычной правки схем; реальные вызовы расходуют квоту.

При изменении архитектурного выбора обновить ADR по правилам `docs/adr/README.md`. Skill не даёт отдельного разрешения на коммит, push или публикацию.
