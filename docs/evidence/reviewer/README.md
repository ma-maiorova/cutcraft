# Проверка реального проверяющего (критика)

Ответственный: Галим. Модуль — `reviewer.py`, инструкция — `prompts/reviewer.txt`.

## Как устроен вызов

1. `review_plan` проверяет задание, каталог и план контрактами.
2. Для каждой сцены читаются кадры её сегмента. Разрешены PNG/JPEG/WebP до 4 МБ; расширение сверяется с сигнатурой файла. SVG-заглушки отклоняются **до** обращения к API — модель их не увидит.
3. Один запрос к `VISION_MODEL_NAME` через общий `model_client.chat_json`: текст (задание, сцены с транскриптом сегмента, неиспользованные сегменты) и кадры как `image_url` с base64 data URL, каждый подписан своим `scene_id`.
4. Клиент перед запросом проверяет по каталогу OpenRouter нулевую цену и наличие `image` во входных модальностях; платного fallback нет.
5. Ответ проходит `validate_review`: решение ровно по каждой сцене, для замечаний непустые issue/evidence/requested_change. Затем элементы упорядочиваются как сцены плана.

Критик получает только стоп-кадры: звук, речь и движение он не проверяет. Он проверяет верность подписи транскрипту, соответствие кадра сцене и пользу сцены для задания; это не фактчекинг утверждений источника.

## Контрольные случаи (`cases/`)

| Случай | Что подложено | Ожидание |
|---|---|---|
| `correct` | Верные подписи, подходящие кадры | accept для всех сцен |
| `lost_caveat` | scene_1: «Метод доказал свою эффективность в реальных условиях» вместо «только на симуляции» | scene_1 — revise_caption (или needs_human_review), остальные accept |
| `wrong_frame` | Кадр сегмента s2 заменён рекламой пляжного отдыха | scene_1 — replace_segment (или needs_human_review), остальные accept |

Кадры — синтетические PNG-иллюстрации (`assets_are_real=false`), нарисованы для проверки, не стоп-кадры видео. Планы написаны вручную, а не монтажёром. Ожидания — в `cases/cases.json`.

Метрики по каждому случаю: **пропуски** (ожидалось замечание, критик принял), **ложные отказы** (ожидалось accept, критик отклонил), **другое решение** (замечание есть, но не того типа).

## Запуск

Нужен локальный `.env` с `OPENROUTER_API_KEY` и `VISION_MODEL_NAME` (бесплатная модель с image input):

```bash
python3 scripts/list_free_vision_models.py      # кандидаты; ключ не нужен
python3 scripts/check_reviewer_live.py          # 3 запроса из дневной квоты
```

Результаты пишутся в `output/reviewer-live-*/` (`*_review.json`, `result.json`). Для фиксации в репозитории скопируйте их в эту папку и обновите таблицу ниже.

### 2. Контрольные случаи после уточнения промпта — [results/prompt_v2/](results/prompt_v2/)

В промпт добавлены правило о языке подписи и требование давать в `requested_change` одну формулировку и не трогать `source_quote`.

- `lost_caveat` — снова верно (`revise_caption` / accept / accept).
- `correct` и `wrong_frame` — **не получены**: модель потратила весь лимит 8000 токенов на рассуждения (≈9200–9400 по её счётчику) и вернула пустой ответ. Код корректно отклонил результат.

Вывод: `dots-3-note-preview` как критик нестабилен — рецензия то укладывается в 70–90 с, то не возвращается вовсе. Нужна модель без длинных рассуждений (например, `gemma-4-31b-it:free`, когда она доступна); ответы этой версии промпта на `correct`/`wrong_frame` ещё не проверены.

### 4. Ветка доработки на двух моделях — [revision/](revision/)

`python3 scripts/check_revision_live.py`: стартовый план — контрольный дефект `lost_caveat`; критик → монтажёр → критик.

- Попытка 1 (`attempt1_failed/`) — критик верно вернул `revise_caption`, но предложил два варианта подписи. Исправленный монтажёром план отклонён контрактом: «Цитата отсутствует в транскрипте сегмента» (монтажёр изменил `source_quote`). Сам ответ монтажёра не сохранился — он отклоняется внутри `planner.model_plan`.
- Попытка 2 (после правила об одной формулировке) — механика сработала: критик вернул одну правку, монтажёр заменил подпись точно, `source_quote` и принятые сцены сохранены (`validate_revision` прошёл). Итог `needs_human_review`: при повторной проверке критик отклонил **не изменённую и ранее принятую** scene_2 («ошибки» вместо «источники ошибок»), хотя ту же подпись дважды принимал.

Исправление по итогам попытки 2: `review_plan(..., previous=...)` — сцены, принятые в прошлом раунде и не изменённые ни в одном поле, сохраняют `accept` без повторного просмотра; модель получает только изменённые сцены (остальные — как текстовый контекст связности). `main.py` передаёт прошлый раунд. Позже это проверено живыми запусками на реальном видео: при повторной проверке критик смотрел только исправленную сцену.

### Ограничения

- По одному прогону на вариант, синтетические иллюстрации, ручные планы. Это не оценка надёжности и не проверка на настоящем видео.
- Критик и монтажёр — одна модель; независимость проверки ограничена.
- `max_tokens`: при 2200 ответ обрезался; 8000 хватает только когда модель рассуждает коротко.

## Что изменилось позже

Результаты выше получены на `dots-3-note-preview:free` и синтетических PNG. Дальше критик работал на `nvidia/nemotron-3.5-super-vl:free` и реальном видео. Его инструкция дополнена правилами о длине заголовка и связности сцен, а `selection_reason` монтажёра ему больше не передаётся. Полный цикл на реальном видео описан в [real_video](../real_video/README.md). Контрольные случаи на новой модели и с новой инструкцией ещё не перезапускались.
