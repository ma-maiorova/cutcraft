# Страница истории запуска

Ответственный: [Кирилл / KirillRatner](https://github.com/KirillRatner). Статус: сделано и влито в main. Формат журнала — в разделе «Журнал событий».

## Назначение

На одной локальной HTML-странице показать, как задание проходит через монтажёра и проверяющего: кто получил какие данные, что вернул и почему потребовалось исправление. Страница строится после завершения запуска из сохранённых результатов.

Страница — это `report.html` в папке запуска: сверху история шагов, ниже итоговая раскадровка. Второго источника состояния нет, модели при открытии страницы не вызываются. Рядом лежит `short.mp4`, собранный по той же итоговой раскадровке.

## Что показать

1. Задание, режим demo/live, признак настоящих материалов и итоговый статус.
2. Последовательность: вход и каталог → монтажёр → проверки кодом → критик → доработка при замечаниях → проверки кодом → повторный критик → результат.
3. Для каждого выполненного шага — исполнитель, краткое описание входа, результат и раскрываемый JSON. Указывать имена связанных артефактов: plan_0.json, review_0.json, plan_1.json и review_1.json. Локальные ссылки необязательны, если JSON встроен в HTML.
4. Решения критика по scene_id с issue, evidence и requested_change. Отдельно показать, какие сцены приняты и какие отправлены на доработку.
5. Сравнение версий по scene_id: подпись, выбранный segment_id, таймкоды и цитата до/после. Если поле не изменилось, обозначить это. Для сцен показать доступные реальные кадры либо явную маркировку условных карточек.
6. Завершение: принятие, оставшиеся замечания для человека или ошибка. При принятии первой версии ветку исправления показать как пропущенную, а не выполненную.

Для сохранённой истории достаточно состояний «выполнено», «пропущено», «ошибка» и «нет данных». Состояние «выполняется» не показывать как реальный прогресс в статическом отчёте.

## Откуда брать данные

Файлы запуска: input.json, plan_N.json, review_N.json, history.json, status.json и журнал events.json. history.json — список пар plan/review, events.json — подробный журнал шагов.

Из сохранённых пар можно восстановить обмен монтажёра и критика и сравнение версий. Нельзя выдумывать отсутствующие длительности, тексты внутренних рассуждений модели, успешное выполнение отдельных проверок или место сбоя. Общая длительность из status.json не является длительностью каждого шага.

Для точного отображения проверок и сбоев оркестратор пишет журнал events.json: порядок события, этап, исполнитель, состояние, входные и выходные артефакты и безопасное сообщение ошибки. События сохраняются по ходу работы, поэтому сбой не уничтожает уже полученные результаты. Контракты каталога, плана и review при этом не менялись.

Для старых запусков без событий выводить только подтверждённые этапы и пометку «подробный журнал отсутствует». Если отчёт строится после ошибки, он должен работать с неполным набором артефактов и показывать сохранённую часть истории.

## Журнал событий `events.json`

Пишет `main.py`, перезаписывает файл после каждого шага. Это вывод оркестратора, а не контракт между ролями: catalog, plan и review не меняются.

```json
{"schema_version": "1.0", "events": [
  {"seq": 4, "stage": "review", "actor": "reviewer", "iteration": 0, "state": "done",
   "inputs": ["plan_0.json"], "outputs": ["review_0.json"], "message": ""}
]}
```

- `stage`: `input`, `plan`, `plan_check`, `review`, `revise`, `revision_check`, `finish`. `iteration`: 0 — первый раунд, 1 — доработка, `null` — вход и итог.
- `actor`: `code`, `planner`, `reviewer`.
- `state`: `done`, `skipped` (доработка не запускалась: всё принято или план передан человеку), `error`. Для `error` в `message` — тип и текст ошибки, до 500 символов; ключей и заголовков в них нет.
- `inputs`, `outputs` — имена артефактов в папке запуска.
- Если этап записан несколько раз, действует последнее событие. Так бывает с `finish`: он записывается как `done` до построения отчёта и как `error`, если отчёт построить не удалось.

Кроме журнала, `input.json` теперь содержит `catalog_path` (для перестройки отчёта) и `models` — имена моделей в live-режиме, без ключа. `plan_N.json` и `review_N.json` сохраняются сразу после своего шага, а при сбое пишутся `history.json` и частичный `report.html`.

Перестроить отчёт по любой папке запуска, в том числе старой без журнала:

```bash
python3 render.py output/<timestamp> [--out файл.html]
```

Кадры при перестройке берутся из каталога по `catalog_path`. У старых запусков без него — из `data/`, `examples/` или снимка [`docs/evidence/real_video/catalog_1a8be59/`](evidence/real_video/catalog_1a8be59/README.md), на котором записаны сохранённые живые прогоны. Кадр берётся только для сегментов, совпадающих с сохранёнными в `input.json`. Остальные помечаются как недоступные: имена файлов у разных каталогов совпадают, и без сверки отчёт показал бы кадр другого сегмента.

## Границы реализации

Журнал, чтение результатов и HTML — часть оркестратора. Монтажёр и проверяющий возвращают данные по общему контракту, отдельного протокола для страницы нет.

Экранировать текст задания, модели, цитат и ошибок при вставке в HTML. Не включать ключи, HTTP-заголовки авторизации и содержимое .env. На странице не должно быть кнопок, которые незаметно запускают API или расходуют квоту.

## Что проверяют тесты

- После `python3 main.py --demo` создаётся локальный отчёт с понятной последовательностью и раскрываемыми входами/выходами.
- В демо с замечанием видны исходная версия, причина исправления, исправленная версия и повторное решение.
- Сценарий без замечаний не изображает несуществующую доработку.
- При needs_human_review понятно, какие замечания остались; при ошибке видны доступные результаты и подтверждённое место сбоя либо «нет данных».
- Старые результаты без нового журнала открываются с явным ограничением детализации.
- Демо и настоящие материалы обозначены раздельно; текст источника отображается безопасно.
- Тесты покрывают пропуск исправления, сравнение по ID, неполную историю и экранирование пользовательского текста.
