# ADR-0005: один контейнер для локального workflow

Дата: 2026-10-16  
Статус: Принято для MVP

## Контекст

Нужен воспроизводимый запуск Python-приложения через Docker. Роли не слушают HTTP-порты и не развёртывают модели: planner и reviewer — функции одного процесса, которые обращаются к внешнему API. Возможные варианты — только локальный Python, один контейнер или отдельный сервис для каждой роли.

## Решение

Упаковать существующий процесс в один образ Python 3.12. Dockerfile по умолчанию запускает фиксированное демо. Compose содержит один одноразовый сервис app; отдельный override включает живой запуск с локальным .env. Результаты пишутся в bind mount output и доступны браузеру на хосте. Сетевые порты не публикуются.

Не менять JSON-контракты и порядок ролей. Не запускать внутри контейнера coding-agent CLI. Не копировать ключи и пользовательское видео в образ. Превью MP4 остаётся отдельным необязательным шагом на хосте; ffmpeg и Pillow в базовый образ не включены.

## Последствия

Одна команда воспроизводит окружение; нет сетевых контрактов, очередей и нескольких сервисов ради двух функций. Для просмотра статического HTML веб-сервис не требуется. У сборки есть зависимость от загрузки базового образа, у live-запуска — от внешнего API. При bind mount на Linux нужно обеспечить права текущего UID/GID на output.

## Пересмотр

Разделить сервисы при реальной необходимости независимого масштабирования, удалённых задач, очереди или многопользовательского интерфейса. Наличие двух LLM-ролей само по себе этого не требует.
