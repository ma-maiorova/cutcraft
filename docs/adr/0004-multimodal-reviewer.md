# ADR-0004: мультимодальный критик — кадры в одном запросе

Дата: 2026-10-15  
Статус: Принято для MVP (PR #3)  
Связь: [проверяющий](../../reviewer.py), [клиент](../../model_client.py), [контракты](../CONTRACTS.md), [результаты](../evidence/reviewer/README.md), ADR-0002, ADR-0003

## Контекст

Проверяющий должен сопоставить подпись сцены с транскриптом и с кадром. Контракт 1.0 передаёт в `review_plan` только локальные пути кадров (`frames`); путь в тексте prompt модель не видит. Нужно определить, как кадры попадают к модели, какие форматы допустимы и как ограничить ожидание бесплатного API.

Альтернативы:
- текстовый критик без изображений — не проверяет соответствие кадра сцене;
- отдельный запрос на каждую сцену — втрое больше запросов при дневной квоте ~50 и без проверки связности трёх сцен;
- публичные URL кадров — требует хостинга и передачи материалов третьей стороне по ссылке;
- локальные эвристики (OCR, классификатор) — отдельная зависимость и не оценивает смысл подписи.

## Решение

Один запрос к `VISION_MODEL_NAME` на проверку всего плана. Сообщение содержит JSON с заданием, сценами (с транскриптом своего сегмента) и неиспользованными сегментами, а затем для каждой сцены — подпись `scene_id` и кадры как `image_url` с base64 data URL. Общий клиент получает необязательный параметр `images`; запрос с картинками разрешён только модели с `image` во входных модальностях по каталогу OpenRouter.

Для реального критика кадры — PNG, JPEG или WebP до 4 МБ, сигнатура файла должна совпадать с расширением, не больше 12 кадров на запрос. SVG и прочие форматы отклоняются до обращения к API; демо-режим их по-прежнему принимает. Формат review 1.0 не меняется: ответ проходит `validate_review`. Strict structured output используется без условных правил схемы (их проверяет код).

Клиент ограничивает общее время ответа (`MODEL_TIMEOUT_SECONDS` на запрос), а не только паузу между пакетами: OpenRouter держит соединение keepalive-байтами, пока модель думает. Ошибки показывают причину провайдера (например, 429 upstream), без ключа и заголовков. Для критика `max_tokens` = 8000, из них не больше 3000 на рассуждения (`reasoning.max_tokens`): без бюджета думающая модель тратила весь лимит на рассуждения и не возвращала ответ.

При повторной проверке после доработки сцены, принятые в прошлом раунде и не изменённые ни в одном поле, сохраняют `accept` без повторного просмотра (`review_plan(..., previous=...)`); модель получает изменённые сцены и, как текстовый контекст, принятые. Это продолжает инвариант `validate_revision` о неизменности принятых сцен; альтернатива — полная повторная проверка — давала случайные отказы по уже принятому тексту.

## Последствия

Модель видит кадры и цитирует их в `evidence`. Три контрольных случая прошли на `dots-studio/dots-3-note-preview:free` (70–90 с на запрос), но эта модель иногда тратит весь лимит на рассуждения и не отвечает. На реальном видео критик работает на `nvidia/nemotron-3.5-super-vl:free`: весь цикл из двух запросов занимает 20–40 с, и в одном прогоне он нашёл заголовок с фактами из соседнего фрагмента. Перенос решений уменьшает объём повторной проверки, но изменённая сцена оценивается без повторного взгляда модели на остальные кадры.

Блок данных должен поставлять растровые кадры: SVG пригодны только для демо, live-запуск на них завершается до API. Реальный каталог `data/` (JPEG) этому требованию соответствует. Кадры base64 увеличивают запрос, отсюда ограничения размера и количества. Модель критика выбирается конфигурацией. Сейчас она совпадает с моделью монтажёра, поэтому независимость проверки ограничена. Частично это компенсирует то, что критик не получает `selection_reason`, то есть аргументы монтажёра. Стоп-кадры не позволяют проверять звук и движение.

## Пересмотр

Новое решение потребуется при переходе на видео или аудио как вход критика, при отказе от base64 в пользу хранилища или URL, при росте числа сцен или кадров сверх лимита одного запроса или при изменении формата review.
