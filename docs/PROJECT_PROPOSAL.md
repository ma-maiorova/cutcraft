# CutCraft — project proposal

Команда 28 · защита 16 октября 2026

## 1. Идея

CutCraft делает короткий ролик из длинного видео. Пользователь пишет, о чём должен быть ролик, а система выбирает три подходящих фрагмента, ставит их в порядок рассказа и пишет к каждому короткий заголовок. Отдельный агент проверяет результат по исходнику и кадрам и возвращает неудачные сцены на исправление. На выходе — план ролика и готовое вертикальное видео.

## 2. Пользователь и проблема

Проект рассчитан на авторов научно-популярных, образовательных и новостных нарезок из интервью и лекций. Найти в длинном видео моменты под конкретную тему и связать их в сюжет — долгая ручная работа.

При сокращении легко исказить смысл, хотя каждое слово в ролике настоящее. Фраза «метод работает, но пока только на симуляции» превращается в заголовок «метод доказан». В наших прогонах монтажёр-LLM делал похожее: приписывал фрагменту вывод из соседнего куска интервью. Проверяющий это ловил.

Экономию времени на реальных пользователях мы не измеряли, это гипотеза.

## 3. Почему LLM и агенты

Выбрать фрагменты под задание можно только по смыслу речи: поиск по словам не отличит тезис от оговорки. Соответствие кадра подписи оценивает модель, которая видит изображения.

Одного вызова модели мало. Монтажёр не видит кадров и иногда добавляет в заголовок то, чего в выбранном фрагменте нет. Проверяющий получает транскрипт, кадры и неиспользованные фрагменты, но не видит объяснений монтажёра, и проверяет план по источнику. Если он находит ошибку, монтажёр исправляет только затронутую сцену.

## 4. MVP

**Вход:** текстовое задание и каталог одного видео. В демо это интервью Бориса Штерна о подтверждениях Большого взрыва: 15 фрагментов на всю речь спикера, с транскриптом, таймкодами и настоящими кадрами. Транскрипт сделан заранее через Whisper, ручная сверка и исправления описаны в [описании источника](../data/SOURCE.md).

**Выход:** одна папка запуска с двумя результатами:

- `report.html` — план из трёх сцен на 20–30 секунд: у каждой кадр, таймкоды, короткий заголовок и дословная цитата. Там же шаги цикла, решения проверяющего и сравнение «было → стало»;
- `short.mp4` — вертикальное видео 9:16 по итоговому плану: заголовок сцены сверху, дословные субтитры снизу.

Заголовок сцены — крупный текст на экране, 4–8 слов. Субтитры берутся из транскрипта, модель их не пишет. Видео собирается кодом по готовому плану, модели в сборке не участвуют.

В MVP не входят поиск видео, загрузка на YouTube, озвучка, музыка, переходы, несколько исходников и анализ звука и движения.

## 5. Архитектура

```text
задание + каталог
      ↓
монтажёр (LLM): 3 сцены, тезис → доказательство → вывод
      ↓
код: сегменты существуют, 20–30 с, цитаты дословные
      ↓
проверяющий (LLM с изображениями): текст + кадры
      ├── всё принято → accepted
      └── замечания → монтажёр исправляет затронутые сцены → код → повторная проверка
                                                         ├── принято → accepted
                                                         └── иначе → needs_human_review
      ↓
сборка видео по итоговому плану (ffmpeg)
```

Оркестратор написан обычным кодом. Порядок шагов, форматы, таймкоды и лимиты известны заранее, и код контролирует их надёжнее модели. Цикл ограничен одним исправлением: в наших прогонах этого хватало, а если нет, решение остаётся за человеком.

Модели вызываются через OpenRouter, только бесплатные варианты `:free`. В текущем шаблоне настроек для обеих ролей выбрана `nvidia/nemotron-3.5-super-vl:free`; сохранённые успешные прогоны на реальном видео получены с ней. Это не сравнительная оценка стабильности моделей. Модель задаётся в `.env`, код от неё не зависит.

Всё упаковано в один Docker-контейнер с Python, ffmpeg и шрифтами. Ключ передаётся только при запуске, исходное видео подключается папкой и в образ не копируется ([ADR-0005](adr/0005-single-container.md), [ADR-0006](adr/0006-shorts-in-container.md)).

## 6. Контракты

| Контракт | Что внутри |
|---|---|
| [Каталог](../schemas/catalog.schema.json) | фрагменты, таймкоды, транскрипт, пути кадров |
| [План](../schemas/plan.schema.json) | три сцены, заголовки, цитаты, обоснование выбора |
| [Проверка](../schemas/review.schema.json) | решение по каждой сцене, замечание, свидетельство, правка |

JSON Schema задаёт форму. `contracts.py` проверяет связи между файлами: существование сегментов, границы, длительность, точное вхождение цитаты в транскрипт, сохранение принятых сцен при исправлении. Техническая проверка не доказывает смысловую точность, это задача проверяющего. Подробнее — в [CONTRACTS.md](CONTRACTS.md).

## 7. Демонстрация

```bash
docker compose -f compose.yaml -f compose.live.yaml run --rm app
```

Результат — `report.html` и `short.mp4` в `output/<timestamp>/`. Порядок показа — в [DEMO_GUIDE.md](DEMO_GUIDE.md).

Новый запуск часто проходит без исправления. Чтобы гарантированно показать, как проверяющий ловит ошибку, есть режим с контрольной ошибкой: код подменяет первый заголовок на «Большой взрыв произошёл вчера в Москве». В нашем прогоне проверяющий это обнаружил, монтажёр исправил заголовок на «13,8 миллиарда лет назад был большой взрыв», повторная проверка приняла план.

Если запуск упал, в отчёте видна сохранённая часть истории ([описание страницы](RUN_HISTORY_UI.md)).

## 8. Что проверено

| Проверка | Результат на 16 октября |
|---|---|
| Автоматические тесты | 67 проходят локально и внутри Docker-образа |
| Монтажёр на учебном каталоге | план и одна контрольная правка, [результаты](evidence/planner/README.md) |
| Проверяющий на контрольных случаях | 3 из 3 на синтетических PNG, [результаты](evidence/reviewer/README.md) |
| Полный цикл на реальном видео | `accepted`, связный сюжет; в другом прогоне найдено и исправлено искажение, [результаты](evidence/real_video/README.md) |
| Контрольная ошибка | обнаружена и исправлена в живом запуске через Docker |
| Видео | собирается в контейнере после живого запуска, 9:16, кириллица в заголовках и субтитрах |

Это единичные прогоны, а не оценка надёжности. Бесплатные модели бывают недоступны (429) или тратят весь лимит токенов на рассуждения. Ответ модели меняется от запуска к запуску. Проверяющий видит стоп-кадры и не слышит звук. Обе роли работают на одной модели, поэтому независимость проверки ограничена: у ролей разные инструкции и данные, но ошибки модели могут совпадать. Верность источнику не означает проверку фактов в мире.
