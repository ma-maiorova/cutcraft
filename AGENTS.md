# CutCraft — инструкции для разработки

## Контекст

CutCraft готовит план короткого ролика из одного заранее подготовленного видео. Вход — задание пользователя и каталог фрагментов с транскриптом, таймкодами и кадрами. Выход — монтажный план, замечания, история доработки и HTML-раскадровка. По готовому плану отдельный скрипт может собрать превью-видео.

MVP: три сцены общей длительностью 20–30 секунд, связанные в сюжет «тезис → доказательство → вывод». Заголовок сцены короткий (4–8 слов), дословные субтитры берутся из транскрипта. Цепочка: монтажёр → проверяющий → одно исправление при замечаниях → повторная проверка → результат или передача человеку. Экспорт MP4 как часть запуска, озвучка, музыка, поиск видео и автопубликация в текущий объём не входят.

Сначала прочитай README.md и docs/CONTRACTS.md. Возможности проверяй по текущей ветке и коду: открытый PR может содержать реализацию, которой ещё нет в main. Если существует AGENTS.local.md, прочитай его как локальные инструкции; файл не должен попадать в Git.

## Модули и границы

- `planner.py`, `prompts/planner.txt` — создание плана и исправление замечаний; блок Марины.
- `reviewer.py`, `prompts/reviewer.txt` — проверка сцен по источнику и изображениям; блок Галима.
- `data/` — каталог, кадры, транскрипт Whisper и описание источника; блок Артёма, инструкции в `blocks/data/`.
- `scripts/render_short.py` — превью-видео по готовому плану. Моделей не вызывает и в агентный цикл не входит; нужен Pillow.
- `main.py`, сохранение состояния и интеграция — блок Кирилла; `render.py` формирует HTML.
- `model_client.py` — общий клиент OpenRouter для всех ролей; свои способы вызова модели не добавляй.
- `contracts.py`, `schemas/` и `examples/` описывают общие интерфейсы; инструкции участников лежат в `blocks/`.

Приложение работает локально на Python, модели вызываются через API OpenRouter; рабочая модель для обеих ролей указана в `.env.example`. Отдельная VM и запуск coding-agent CLI внутри приложения не требуются. Соблюдай режим бесплатных моделей; не добавляй платный fallback. Реальные вызовы расходуют квоту, поэтому для обычной отладки используй демо.

## Контракты и достоверность

Сохраняй интерфейсы модулей и формат 1.0; изменения общих контрактов согласовывай с командой и обновляй затронутые проверки и примеры вместе с кодом. Длительность, границы и ссылки на фрагменты проверяет код. Принятые сцены при доработке сохраняются; автоматический цикл ограничен одной доработкой.

`examples/` — неизменные контрольные примеры; реальные материалы лежат в `data/`.

Демонстрационные ответы и условные кадры явно отличай от реальных API-вызовов и настоящих материалов. Передача пути к изображению в prompt не передаёт модели изображение. Успех демо не доказывает работу реального проверяющего или готовность всей системы. Проверка верности источнику не является независимым фактчекингом.

## Изменения и проверка

Не коммить ключи, реальные .env, пользовательские видео и output. Не удаляй существующий Java-шаблон и настройки IDEA без задачи. Не включай чужие локальные изменения в свой коммит.

После изменений запускай `python3 -m unittest discover -s tests -v` и `python3 main.py --demo`. Сообщай фактические результаты и ограничения проверки. README должен описывать работающий код текущей ветки.

## Проектные skills

Skills хранятся в `.agents/skills/`. Codex находит их автоматически; другой coding-agent должен открыть нужный SKILL.md явно. Это инструкции для разработки, а не runtime-роли монтажёра и проверяющего: их инструкции лежат в `prompts/`.

- `cutcraft-pr-preflight` — проверка перед PR: diff, тесты, демо, контракты и отсутствие секретов.
- `cutcraft-contracts` — изменения каталога, плана и замечаний: JSON Schema, runtime-проверки, примеры и совместимость.
- `cutcraft-adr` — создание и пересмотр архитектурных решений в `docs/adr/`.

Успешная проверка сама по себе не разрешает push или merge.
